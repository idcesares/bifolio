# Performance, milestone M2 (paged reader)

Spec: PRF-02, PRF-04. Measured by the debug build logging `BifolioPerf` (only when the app is debuggable), read with
`adb logcat -s BifolioPerf`.

## Caveat

All numbers come from the Android Studio emulator `Medium_Phone_API_37.0` (x86_64, software GPU, debug build, no
baseline profile, R8 off, host Windows 11). It is a floor for the real work, not a device result: expect a physical
phone to be several times faster, but this is not proven here. The reference foldable was not available. These
numbers do not close PRF-04; they only show where the time goes.

## Against the budgets

| Budget | Target | Measured on the emulator | Verdict |
|---|---|---|---|
| PRF-02 first spread of a 100 KB document | under 500 ms P50 | 756 ms for 692 B, 1299 ms for 284 KB | exceeded here, includes process start and JIT |
| PRF-04 visible spread after a geometry change | under 100 ms | 393 ms provisional after rotation | exceeded here |
| PRF-04 full pagination of 1 MB | under 3 s, off the main thread | 16.5 to 25.3 s | exceeded by about 5 to 8 times here |

The main thread is never used for pagination: it runs on `Dispatchers.Default` and is cancelled when the geometry
changes. The numbers are not masked or extrapolated. Likely contributors, not yet profiled: debug build and JIT warm
up, one `StaticLayout` per block on first measure, the 1 MB document having mostly short blocks. A device run with a
release build and a baseline profile (M6) is needed before judging the budget. Profiling the paginator (block
measure cache reuse, avoiding re-measuring across the canonical stage) is the first candidate if a device also misses.

## Profiling of the full pagination (follow-up)

Method: a temporary in-app harness (removed, not committed) parsed the generated corpus and ran
`Paginator.paginateAll` with the production `StaticLayoutBlockMeasurer` wrapped in a timer, on the same emulator, 1080x2400.
A JVM run with `FakeBlockMeasurer` isolates the paginator.

| Measurement | Result |
|---|---|
| JVM, paginator only, fake measurer, about 215k words (1 MB), 2792 blocks | 54 ms |
| Measure calls | 1374 for 1061 blocks (C-02), 4854 for 3774 blocks (1 MB): about 1.3 per block, one per (block, width) plus table cells |
| Emulator C-02, debug build, JIT only, pass 0 | 10.2 to 16.0 s (reproduces the 10.7 s above), measurer 7.1 to 11.2 s |
| Emulator C-02, after `cmd package compile -f -m speed` | 2.4 s first pass, 1.2 to 1.8 s warm, measurer about 70% |
| Emulator 1 MB, speed-compiled | 5.1 s first pass, 4.2 s warm, measurer 3.0 to 3.4 s (about 0.62 ms per call) |
| Emulator, plain CPU loop of 2e8 iterations | 10 to 42 s depending on run and compile state: roughly 4x run to run noise |

Findings:

- No algorithmic defect. Pagination is linear, every block is measured once per geometry (also across the provisional and
  canonical stages), guarded by `PaginationComplexityTest` (exact call count equal to one layout per block, and at most
  2.2x calls when the document doubles).
- The 10 to 25 s were dominated by ART running the debug build with the JIT cold: the same work is 4 to 8 times faster
  once the app is AOT compiled. Parsing alone took 28 s cold and 0.65 to 1.4 s compiled for 284 KB.
- With AOT, the remaining cost is `StaticLayout` (high quality breaking plus hyphenation) at about 70% of the time.
  1 MB is still about 4.2 to 5 s on this emulator, above the 3 s budget (PRF-04 is not closed). The emulator is
  tens of times slower than the host for plain code, so a phone is expected to be faster, but that is not proven.

Next steps, not implemented (larger change):

1. Run on a physical device or the reference foldable with a release build and baseline profile (M6) before investing.
2. If still over budget: bounded parallel measurement (the measurer is stateless): worker threads pre-measure blocks ahead
   of the composer into a shared per-block array, cancellable through `CancellationSignal`. Projection only: up to about
   3x on the measurer share with 6 cores.
3. Alternatively, incremental pagination: the canonical pass beyond the anchor window only needs to finish before the
   user jumps far, so it can run at low priority and report progress.
