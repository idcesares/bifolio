# Performance, milestone M2 (paged reader)

Spec: PRF-02, PRF-04. Measured by the debug build logging `BifolioPerf` (only when the app is debuggable), read with
`adb logcat -s BifolioPerf`.

## Caveat

All numbers come from the Android Studio emulator `Medium_Phone_API_37.0` (x86_64, software GPU, debug build, no
baseline profile, R8 off, host Windows 11). It is a floor for the real work, not a device result: expect a physical
phone to be several times faster, but this is not proven here. The reference foldable was not available. These
numbers do not close PRF-04; they only show where the time goes.

Times are from the request to the stage (provisional, canonical, complete) or to the first painted spread.
The second C-02 cold run produced no log line before my wait timed out and is not reported.

## Against the budgets

| Budget | Target | Measured on the emulator | Verdict |
|---|---|---|---|
| PRF-02 first spread of a 100 KB document | under 500 ms P50 | 756 ms for 692 B, 1299 ms for 284 KB | exceeded here, includes process start and JIT |
| PRF-04 visible spread after a geometry change | under 100 ms | 393 ms provisional after rotation | exceeded here |
| PRF-04 full pagination of 1 MB | under 3 s, off the main thread | 16.5 to 25.3 s | exceeded by about 5 to 8 times here |

The main thread is never used for pagination: it runs on `Dispatchers.Default` and is cancelled when the geometry
changes. The numbers are not masked or extrapolated. Likely contributors, not yet profiled: debug build and JIT warm
up, one `StaticLayout` per block on first measure, the 1 MB document having mostly short blocks. A device run with a
release build and a baseline profile (M6) is needed before judging the budget. Profiling the paginator (block
measure cache reuse, avoiding re-measuring across the canonical stage) is the first candidate if a device also misses.
